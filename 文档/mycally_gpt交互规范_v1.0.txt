《mycally 与 GPT 协作开发交互规范（v1.0）》
作者：Huixuan（阿帅）
目标：降低 mycally 的耦合度、提升可读性与可扩展性，通过“可复用提示模板 + 严格边界 + 迭代验收清单”实现稳定演进。
参考基线：cally.py（原版干净实现）与 mycally.py（现有功能更丰富但耦合偏高）。

===============================================================================
1. 范围与目标
===============================================================================
1.1 目标
  1) 将 mycally 重构为分层、可测试、易扩展的代码库；
  2) 保持现有外部行为不变（CLI 参数、输出格式、单元测试基线）；
  3) 引入模块边界与接口契约，便于增量添加“条件流(if/while/switch)”“线程/任务”语义。

1.2 范围
  1) 仅对 mycally.py 进行增量升级；
  2) 不删除现有功能与按钮（若存在 GUI）；
  3) 必要时可从 cally.py 同步“干净实现”的思路/函数签名。

1.3 非目标
  1) 不更改输入文件格式与命令行参数含义；
  2) 不引入复杂第三方库（除标准库与 networkx/graphviz 可选）。

===============================================================================
2. 目录结构与模块化拆分建议（里程碑）
===============================================================================
2.1 分层设计（建议）
  L0/CLI层：参数解析、任务路由（argparse）
  L1/解析层：RTL 解析（lexer-like），抽取函数、调用、条件块、线程语义
  L2/中间模型层：FunctionDB（函数表）、Edge（调用/条件）、ThreadInfo、CFG 片段
  L3/分析/变换层：构造 caller/callee 关系、强连通、条件边归并、外部符号标注
  L4/输出层：DOT/ASCII 渲染、单元测试快照

2.2 里程碑
  M1：抽离“文件遍历与正则解析”为 Parser 类，纯函数单元测试覆盖
  M2：引入 FunctionDB 与 DTO（dataclass），去除 dict 深层嵌套耦合
  M3：渲染层独立（DotRenderer/AsciiRenderer），消除 print 散布
  M4：条件语义（if/while/switch）提取与统一编码（Edge.kind）
  M5：pthread_create/join 线程语义建模与渲染钩子
  M6：性能回归与大文件健壮性（流式/生成器）

===============================================================================
3. 与 GPT 的交互基本准则（每轮都遵守）
===============================================================================
3.1 输入-输出-约束-证据格式（IOCE）
  【输入】给出当前文件片段/接口签名/失败测试
  【输出】期望的函数/类/补丁（明确返回值/副作用）
  【约束】不得修改的接口/性能目标/异常处理策略
  【证据】小型用例 + 预期输出（或补丁 diff）

3.2 修改边界
  1) “最小侵入”：仅改与本次目标直接相关的函数/类；
  2) “可回退”：新增文件或函数，原函数仅做调用转发；
  3) “行为不变”：CLI、日志和已存在单测输出保持一致（除非本轮目标就是修正）。

3.3 输出形式
  1) 优先给“补丁风格”：说明新增/修改的函数清单 + 完整可运行代码块；
  2) 代码块必须自包含（import、类型、注释齐全）；
  3) 禁止伪 API；若需外部库，先给出替代方案或可选分支。

3.4 命名与风格
  1) Python 3.8+，类型注解，PEP8；
  2) dataclass 用于数据模型（Function, Edge, ThreadInfo）；
  3) 纯函数优先；副作用集中在渲染与 I/O 层；
  4) 日志使用 logging 模块（不直接 print，除渲染层）。

4. Prompt 模板（直接复制使用）
===============================================================================
4.1 重构-抽离解析层
【输入】给定 mycally.py 当前版本的“文件遍历与正则解析”代码（不贴全部，聚焦 parse 函数）。
【输出】给出 Parser 类（parse_files, parse_line），返回 FunctionDB；保留所有现有逻辑。
【约束】不得修改 CLI；必须兼容 cally.py 的 unit_test 语义路径；时间与空间复杂度不高于现状。
【证据】提供 2 个最小 RTL 片段用例，展示解析后 FunctionDB 的结构（json-like）。

4.2 建模-引入中间数据结构
【输入】当前函数表是 dict 深层嵌套（calls/refs/callee_calls 等）。
【输出】定义 dataclass：Function{name, files, calls:set, refs:set, callee_calls:set, meta:dict}，
         Edge{src, dst, kind:str, attrs:dict}，ThreadInfo{thread, task, tail}；并给出由旧结构到新结构的迁移函数。
【约束】迁移函数纯函数；保持单测期望字符串完全一致（graph/ASCII）。
【证据】迁移前后对同一输入的 full_call_graph 输出完全相同（给出断言）。

4.3 渲染层隔离
【输入】当前 full_call_graph/dump_path 中混杂 print 和逻辑。
【输出】实现 DotRenderer/AsciiRenderer，提供 render_graph(function_db, options)；
【约束】功能等价 mycally.py 现状；支持 no_externs/exclude/max_depth；
【证据】用 3 组调用链快照比较（字符串行集合对比）。

4.4 条件语义统一（if/while/switch）
【输入】mycally 里对 if/while/switch 的判定分散，且带计数器状态机。
【输出】新增 ConditionExtractor，输出 Edge(kind="if"/"while"/"switch", dashed=True, group=idx)。 
【约束】不得改变原有连线，只能“叠加语义属性”；
【证据】给出 DOT 片段，验证条件节点以虚线表示，且 switch 同组分支回汇正确。

4.5 线程语义（pthread_create/join）
【输入】当前通过 myinfo/mycalls 维护线程与任务尾节点。
【输出】ThreadLinker：将 pthread_create 映射到 ThreadInfo，并渲染 “tail -> join” 语义边；
【约束】不破坏 caller/callee；失败时降级为普通调用边；
【证据】给出最小示例与最终 DOT。

4.6 回归测试与 CI 钩子
【输入】现有 unit_test_* 参考输出。
【输出】pytest 风格用例：构造 function_db -> 调用渲染 -> 比对快照；
【约束】测试可在无外部文件的情况下运行；
【证据】给出 3 个测试函数与断言。

===============================================================================
5. 每轮迭代交付清单（Checklist）
===============================================================================
5.1 你给 GPT 的输入
  1) 本轮目标一句话；
  2) 受影响的函数/类名清单；
  3) 相关片段/错误堆栈/失败用例；
  4) 接口契约（不允许修改的签名与行为）。

5.2 GPT 必须返回
  1) 补丁清单（新增/修改/删除）+ 风险点；
  2) 完整可运行代码块（或最小可合并 diff）；
  3) 用例与断言（覆盖 happy path 与 corner case）。

5.3 验收标准（DoD）
  1) 通过既有单测（包括 cally.py 的 unit_test 基线思想）；
  2) 新增单测覆盖率 ≥ 1 个典型 + 1 个边界；
  3) 代码无未定义 API，无隐藏全局状态；
  4) 渲染输出与上一版本在非目标部分完全一致。

===============================================================================
6. 质量与工程要求
===============================================================================
6.1 性能
  1) 文件流式读取（fileinput / 生成器）；
  2) 正则复用已编译 Pattern；
  3) 大输入下 O(N + E) 级处理，不引入 O(N^2) 组合。

6.2 日志与错误
  1) logging.getLogger(__name__)；
  2) 解析失败“跳过+告警”，不崩溃；
  3) 渲染失败返回错误信息与最小上下文。

6.3 提交规范
  1) 提交信息：feat/refactor/fix/test + 简短说明；
  2) 变更说明包含：影响范围、回滚方式、验证方法。
